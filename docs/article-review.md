# 記事の内容確認（人間がやる）

記事は Claude が書き、**公開（main へのマージ）の前に人間が内容を確認**します（WEBAPP_BASELINE.md §10-7）。
PR を出すと Cloudflare のプレビュー URL ができるので、そこで実際のページを見て確認します。直したい点は PR のコメントか Claude への指示で伝えてください。

## 毎回見ること

| # | 観点 | 見るところ |
|---|---|---|
| 1 | 事実の正しさ | 分野の説明に間違いや言い過ぎがないか |
| 2 | アプリとの一致 | 記事の説明（ボタン名・手順・条件）がいまのアプリの動きと合っているか。画面写真が古くないか |
| 3 | 表の内容 | 表は計算で作っているので書き間違いはないが、選んだ例や結果が実際に自然か |
| 4 | 日本語・英語の自然さ | 直訳っぽい言い回し、用語の不統一 |
| 5 | 検索用の文言 | 各記事の `title` と `description`（`scripts/pages/<slug>.mjs` の先頭）が、狙う検索語を含み、内容と合っているか |
| 6 | 権利 | 著作権のある歌詞・曲・画像を使っていないか |
| 7 | スマホ | 390px 前後の幅で読みやすいか（表は横スクロール） |

## 今回（2026-10-24、最初の記事 7 本）特に見てほしいところ

| # | 記事 | 確認してほしい点 |
|---|---|---|
| A | tempo-markings | 速度記号の「BPM の目安」の範囲は一般的な資料（英語版 Wikipedia などに載っている値）に頼った。資料によって違う。日本のメトロノームの目盛りと比べて違和感がないか。読み（カタカナ）と意味の訳も |
| B | tempo-markings | 「拍が 4分音符でないとき」の換算（♩. = 60 → ♩ = 90 など）と、アプリが数字をそのまま 4分音符として使うという説明 |
| C | photo-tips | 比較は実際の写真ではなく、同じ画像を加工した 6 枚（傾き 10°、斜め、影、ぼかし、縮小）。本文でもそう書いた。結果（ぼけ 73.4%、傾き 86.5%、影はテンポだけ見落とし）を一般化しすぎていないか |
| D | photo-tips | 撮り方のコツ（300dpi、フラッシュを避ける など）は一般知識。スマホのスキャンアプリを勧めてよいか |
| E | fix-errors | 「よくある間違い」の表は、OMR で一般に起こりやすいものを書いた（このアプリで一つずつ確かめたものではない）。複数小節休符の件だけは CLAUDE.md の既知の弱点 |
| F | musicxml | MusicXML の歴史（2004 年に Recordare、今は W3C Music Notation Community Group、最新版 4.0）。MuseScore のメニュー名（ファイル → 開く／エクスポート） |
| G | what-is-omr | 「1960 年代から研究」、homr の仕組み（セグメンテーション → 五線を切り出してまっすぐに → トランスフォーマーで段ごとに読む）の説明が言い過ぎでないか。homr のコード（モジュール名）から読み取った範囲で書いた |
| H | faq | 「歌詞・コードネーム・強弱は読み取らない」は homr の MusicXML 出力のコードで確認。タブ譜・手書きは非対応と書いた |
| I | guide ほか | 画面写真は PC（1280×800）だけ。アプリがスマホ未対応のため、スマホの画面写真は載せていない |
| J | 全体 | 見本の楽譜は「歓喜の歌」（ベートーヴェン、パブリックドメイン）をスクリプトで 2 段に編曲したもの。作曲者表記「L. van Beethoven」でよいか |
